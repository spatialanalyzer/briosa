# SA 2024 licensed probe session (#277) — 2026-10-07

A maintainer-authorized, bounded probe session for
[#277](https://github.com/spatialanalyzer/briosa/issues/277) ran
`tools/Briosa.LicensedProbes` against one licensed SpatialAnalyzer
`2024.1.0508.5` instance on 2026-10-07, following the
[licensed probe session runbook](../licensed-probe-session.md). Each phase used
exactly one SDK client and started from a clean SA instance with the fixture
job reopened. SA was closed without saving after every phase.

- **Public-API phase.** The generated gRPC client ran against one packaged
  Briosa server. The server log shows its worker runtime-verified the
  activated SDK as an exact match for `2024.1.0508.5`.
- **Worker phase.** The harness hosted one unchanged `Briosa.Worker.exe` from
  the same package, with no server. The worker runtime-verified the activated
  SDK as `2024.1.0508.5`. The operator attested the connected SA release as
  `2024.1.0508.5` (reference `probe277-2024-sa-statusbar`).

For this session, the operator switched the machine-wide SDK COM registration
to the 2024 SDK. Afterwards it was restored to the `2026.1.0529.7`
registration and verified identical to the pre-session backup.

These are observations of one bounded session on one machine, not vendor
guarantees. The harness records hold only labels, step text, dispositions, MP
codes, output retrieval, and counts of harness-created objects. This summary
adds the operator's observations under the same limits: no argument or
returned values, fixture-manifest contents, paths, or license data. As with
the [string-setter record](string-setters-2026-09-28.md), only this reviewed
summary is committed; the raw JSON and markdown records stay with the
operator. Nothing here is transferred from the SA 2026 session, which ran
earlier the same day and has its own record in the 2026 target
(`targets/2026.1.0529.7/docs/testing/evidence/probe-277-2026.1.0529.7-2026-10-07.md`).

## Probe #11: outcome unknown

In public run 1, the server dispatched `p11` (Construct Polygonized Surface
from Point Clouds, Mesh Orientation via `SetStringArg`, 5 × 5 grid cloud)
about 5 ms after `p10` resolved, according to its audit log. Just before
that, `p08`, `p09-circle`, `p09-line`, and `p10` had each returned MP code
`-1` with SDK durations of 5 to 12 ms. SA showed a modal "Encountered an
improper argument." dialog from those steps. It was still on screen when
`p11` was dispatched, and the operator dismissed it a few seconds later.

No MP result arrived before the harness's 120 s client deadline
(`DeadlineExceeded`). The server's long-running execution budget was 600 s.
During the wait, SA stayed idle, while the `SpatialAnalyzerSDK` process used
about one core.

The stall is therefore confounded by the preceding modal dialog. This record
treats the outcome of `p11` as unknown, possibly caused by that dialog, and
not as evidence that the Mesh Orientation substitution hangs. #11 needs a
re-probe in isolation, with no preceding dialog.

After the stop, the `SpatialAnalyzerSDK` process activated by this run's
worker survived SA's exit, and the operator stopped it (see
[SDK process ownership](#sdk-process-ownership-252)).

## Probe #22: inconclusive

During `p22`, SA showed the harness's prompt to select vector group
`B277::VG1` and confirm. The operator selected `VG1` in the tree, then
middle-clicked the graphics view, which panned the view, and then pressed
Enter in the graphics view. SA returned MP code `3` about 43 s after dispatch,
with no output.

In this session, MP code `3` consistently accompanied modal dialogs that the
operator dismissed: the blank plane names in #5 and #6 and the zero-match
wildcard checks. So MP code `3` here most likely means that the runtime
selection was not completed, not that the getter failed. How SA expects a
runtime selection to be confirmed is not known, so #22 is inconclusive.
