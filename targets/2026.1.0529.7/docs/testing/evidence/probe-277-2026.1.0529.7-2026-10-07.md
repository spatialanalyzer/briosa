# SA 2026 licensed probe session (#277) — 2026-10-07

A maintainer-authorized, bounded probe session for
[#277](https://github.com/spatialanalyzer/briosa/issues/277) ran
`tools/Briosa.LicensedProbes` against one licensed SpatialAnalyzer
`2026.1.0529.7` instance on 2026-10-07, following the
[licensed probe session runbook](../licensed-probe-session.md). Each phase used
exactly one SDK client and started from a clean SA instance with the fixture
job reopened. SA was closed without saving after every phase.

- **Public-API phase.** The generated gRPC client ran against one packaged
  Briosa server. The server log shows its worker runtime-verified the
  activated SDK as an exact match for `2026.1.0529.7`.
- **Worker phase.** The harness hosted one unchanged `Briosa.Worker.exe` from
  the same package, with no server. The worker runtime-verified the activated
  SDK as `2026.1.0529.7`. The operator attested the connected SA release as
  `2026.1.0529.7` (reference `probe277-2026-sa-statusbar`).

These are observations of one bounded session on one machine, not vendor
guarantees. The harness records hold only labels, step text, dispositions, MP
codes, output retrieval, and counts of harness-created objects. This summary
adds the operator's observations under the same limits: no argument or
returned values, fixture-manifest contents, paths, or license data. As with
the [string-setter record](string-setters-2026-09-28.md), only this reviewed
summary is committed; the raw JSON and markdown records stay with the
operator. Nothing here is transferred from the SA 2024 session, which has its
own record in the 2024 target
(`targets/2024.1.0508.5/docs/testing/evidence/probe-277-2024.1.0508.5-2026-10-07.md`).

## Probe #11: outcome unknown

In public run 1, the server dispatched `p11` (Construct Polygonized Surface
from Point Clouds, Mesh Orientation via `SetStringArg`, 5 × 5 grid cloud)
about 6 ms after `p10` resolved, according to its audit log. Just before
that, `p08`, `p09-circle`, `p09-line`, and `p10` had each returned MP code
`-1` with an SDK duration under 10 ms. SA showed a modal "Encountered an
improper argument." dialog (OK only), attributed to those steps. The dialog
did not block their MP results. It could not have been dismissed in the 6 ms
before `p11` was sent, so `p11` was dispatched while it was on screen. The
operator dismissed it, and no dialog was visible for the rest of the wait.

No MP result arrived before the harness's 120 s client deadline
(`DeadlineExceeded`). The server's long-running execution budget was 600 s.
During the wait, SA's CPU was idle, while the `SpatialAnalyzerSDK` process
used about one full core.

The stall is therefore confounded by the preceding modal dialog. This record
treats the outcome of `p11` as unknown, possibly caused by that dialog, and
not as evidence that the Mesh Orientation substitution hangs. #11 needs a
re-probe in isolation, with no preceding dialog.

Recovery followed the runbook. `stop-sdk` failed because the polygonize
exchange was still in flight. Stopping the server took its worker down. SA
was closed without saving, and the operator stopped the residual
`SpatialAnalyzerSDK` process (see [SDK process ownership](#sdk-process-ownership-252)).

## Probe #22: inconclusive

During `p22`, SA showed the harness's prompt to select vector group
`B277::VG1` and confirm. The operator selected `VG1` in the tree and pressed
Enter. SA returned MP code `3` about 54 s after dispatch, with no output.

In this session, MP code `3` consistently accompanied modal dialogs that the
operator dismissed: the blank plane names in #5 and #6 and the zero-match
wildcard checks. So MP code `3` here most likely means that the runtime
selection was not completed, not that the getter failed. How SA expects a
runtime selection to be confirmed is not known, so #22 is inconclusive.

## SDK process ownership (#252)

- **Watchdog kill.** In fixture attempt 1, after the watchdog terminated the
  worker, `stop-sdk` returned `incident_kind` `WATCHDOG_TERMINATED`, and the
  server was stopped. The `SpatialAnalyzerSDK` process that the terminated
  worker had activated was still running more than 20 s after SA exited. The
  operator stopped it.
- **Worker taken down with an exchange in flight.** In public run 1,
  `stop-sdk` failed because the `p11` exchange was still in flight. As
  documented with F3, stop waits behind an in-flight call. Stopping the server
  took its worker down. The SDK process activated by that worker was still
  running more than 15 s after SA exited. The operator stopped it.
- **Clean stop.** After fixture attempt 2, a clean `stop-sdk` left no SDK
  process behind. Postflight passed at the end of the session.

The optional #252 ownership probes (worker crash, watchdog kill, parent death)
were not part of this session. These observations come from the recoveries
above.
